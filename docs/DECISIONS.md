# Журнал решений

Формат: номер, дата, решение, причина. Новое решение — в конец. Отменять старое только новой записью.

- **D1 · 2026-10-08 · Старое приложение v0.5 не святыня.** Его можно заменить новой моделью; данные пользователя при этом переносим миграцией (ТЗ §23), а не выкидываем. Новый код в `js/`, `app.js` не растим.
- **D2 · 2026-10-08 · Много файлов `js/`, без сборки и без ES-модулей.** Классические `<script>` + глобал `SM`, каждый файл работает и в Node для тестов. Отменяет прежнее «три файла» из старого AGENTS.md.
- **D3 · 2026-10-08 · Неизвестное = `null`, не 0.** Расчёт с неизвестным входом даёт «неизвестно» и список недостающих данных (ТЗ §2, UNKNOWN != NO).
- **D4 · 2026-10-08 · Геометрия — контур стен «черепашкой»** (длина + поворот), не координаты. Причина: пользователь вводит размеры рулеткой, правка длины должна пересчитывать всё; координаты выводятся.
- **D5 · 2026-10-08 · Формулы: текст → AST, свой интерпретатор.** Без `eval`. Единицы на первом этапе — метки и таблица пересчёта, не полная проверка размерностей.
- **D6 · 2026-10-08 · Не выдумываем строительные данные.** Нормы расхода, цены, упаковки брендов — только от пользователя; иначе `null`/UNKNOWN и вопрос (ТЗ §21).
- **D7 · 2026-10-08 · Тестовая ванная (ТЗ §21) — данные в `js/seeds.js`, не код.** Решение владельца: углы 90° по умолчанию (малая погрешность не критична); «fortan» — перегородочный блок (материал стены, как кирпич). С углами 90° шесть стен замыкаются однозначно (квадрат 4×4 м с выступом 0.5×0.5, пол 15,75 м²). На какой стене двери/окно, где начата плитка, какая зона ГКЛ красится — неизвестно (`null`), не выдумываем.
- **D8 · 2026-10-08 · Работа ведётся разными ИИ-ботами через патчи.** Каждый бот обязан читать `AGENTS.md` → `ARCHITECTURE.md` → `ROADMAP.md` → `DECISIONS.md` и в конце обновить их и `CHANGELOG.md`.
- **D9 · 2026-10-08 · Проём может не иметь привязки к стене** (`wallId: null`, но `roomId`). Общая площадь стен считается верно; по отдельным стенам — нет, и это видно в `issues`.
- **D10 · 2026-10-08 · Состояние хранится как `state["поверхность.слой"]`, по умолчанию UNKNOWN.** Существующее, созданное не нами — в `observations`; что хочет пользователь — в `goals`; уже купленное — в `purchased`. Новое хранилище `stroysmeta:model` отдельно от старого `stroysmeta:v3` (старое не трогаем до Фазы 11).
- **D11 · 2026-10-08 · Новое приложение — отдельная страница `new.html`**, старый `index.html` не трогаем до Фазы 11 (перенос данных). Форма хранения плана: `S={object, techs, materials, plan, fin, bought}`; пока технология = плоский список операций (граф — позже, поле `ops` останется).
- **D12 · 2026-10-08 · Размер короба в тестовой ванной взят условно 0.6×0.4×2.7 м** (владелец разрешил выбрать; помечено `assumed`).
- **D13 · 2026-10-08 · Цена материала — за упаковку; без «в упаковке» стоимость закупки неизвестна (`null`)**, а не считается за единицу.
- **D14 · 2026-10-15 · Библиотека процессов и правил — данные в `S.library`, копия живёт в проекте** (старый проект не меняется от обновления демо-библиотеки). Процесс применяется ко всем поверхностям своего вида в помещении (все стены, а не выбранные) — выбор конкретных стен будет следующим шагом. Порядок процессов в демо-библиотеке — пример структуры, не строительная норма; помечено `demo:true`.
- **D15 · 2026-10-15 · Неизвестное в правилах:** условие с неизвестным (U) не срабатывает молча; если у правила есть `ask`, система задаёт вопрос. Процесс, чьё `needed` неизвестно, получает статус «Требует уточнения».
- **D16 · 2026-10-15 · Технология привязана к процессу полем `processId`; пункт плана хранит `processId`.** Если процесс в состоянии DONE (сделан или не нужен), пункт плана остаётся в списке, но в смету и закупку не входит (`R.skipped`). Один процесс может иметь несколько технологий-альтернатив.
- **D17 · 2026-10-15 · Маршрут = шаги + допущения, считается на копии объекта.** Цена маршрута = его шаги + остальные пункты плана, которые после него ещё нужны. «Дешевле» объявляется только если все маршруты посчитаны полностью. Библиотека обновляется только добавлением (`upgradeLibrary`, версия 2 добавила процесс «Ремонт существующей стяжки»), правки пользователя не затираются.
- **D18 · 2026-10-15 · Чек-лист приёмки = заметки операций с `cat:'accept'`** (тот же источник, что в старом приложении; условия — `cond`, частые ошибки — `error`). Отдельного поля checklist нет. Статус пункта плана — `item.status`, отметки — `item.checks`. Выполненная/принятая работа остаётся в смете, даже когда её процесс стал DONE (пропускаются только ещё не начатые).
- **D19 · 2026-10-15 · Данные нового приложения: ничего не заменяется молча.** Любая подмена текущих данных (откат, файл, облако) идёт через `SM.store.replace`: сначала точка отката текущих. Облако перезаписывается автоматически только если оно не менялось с последней синхронизации (`lastSync` против `updated`); иначе — конфликт, решает человек, перезапись облака только по явному «ОК». Первое подключение к уже существующему облаку — всегда конфликт (решает человек). «Отмена» в конфликте ничего не меняет (в старом приложении отмена перезаписывала облако — здесь нет). Токен Gist лежит отдельно (`stroysmeta:model:sync`) и не попадает в проект, экспорт и облако. Файл в Gist — `stroysmeta-model.json` (отдельный от старого `stroysmeta.json`, чтобы не затереть данные старого приложения).
- **D20 · 2026-10-15 · Excel нового приложения:** неизвестное — пустая ячейка, а не 0; при неизвестных данных в итоге добавляется строка «Итог неполный». Данные листов считает `SM.store.sheets` (без DOM), файл пишет UI через SheetJS.
- **D21 · 2026-10-15 · Факт отдельно от сметы.** Факт лежит в `plan[].fact` ({ops:{opId:{qty,cost}}, mats:{matId:расход}}), смета его не читает и не меняется. Не указано = `null` (неизвестно). Факт вносится после начала работы и закрывается при приёмке. «Остаток» = куплено − израсходовано; если неизвестно хоть одно — остаток неизвестен.
- **D22 · 2026-10-15 · Утверждённая смета = неизменяемый снимок значений** (`S.approved[]`, только добавление, без удаления из UI). Сравнение со сметой «сейчас» показывает разницу итога только если обе сметы полные; иначе пишет, что сравнить итог нельзя.
- **D23 · 2026-10-15 · Версия технологии = неизменяемый снимок, создаётся автоматически при постановке в план** (и вручную «Зафиксировать версию»), только если содержимое изменилось. Пункт плана закреплён на версии (`techVer`) и считается по ней; правка или удаление текущей технологии его не меняет. Обновить пункт до текущей технологии можно только явно и только пока работа не начата (начатая работа остаётся на своей версии, чтобы факт и приёмка не «уезжали»). Старые проекты при загрузке закрепляются на текущей технологии без изменения цифр. Версионируются технологии, а не библиотека процессов (она и так только пополняется, D17). Маршруты считают гипотетические шаги по текущей технологии.
- **D24 · 2026-10-18 · Перенос объектов старого приложения — в ТЕКУЩИЙ проект, добавлением.** В новой модели один объект на проект, поэтому старый объект добавляется в него помещениями (повторный перенос и перенос нескольких объектов не затирают друг друга; пункты и помещения помечены `legacyObjectId`). Перенос атомарный (на копии) и с точкой отката. Старые данные не меняются. Известные отличия: в старом объекте объёмы считались по сумме помещений, в новом — по помещениям (итог тот же); ручной объём этапа применяется один раз (на первом подходящем помещении); 0 в размерах помещения = «неизвестно»; сметы нескольких старых объектов в одном проекте суммируются (раздельные итоги по объектам — не сделаны).
- **D25 · 2026-10-18 · `skipOps` и `opQty` у пункта плана.** Пункт плана может не включать часть операций технологии и переопределять объём операции. Это нужно для переноса и для «этап применён не целиком»; версия технологии не размножается.
- **D26 · 2026-10-18 · Знания из Obsidian — одноразовый перенос в отдельный справочник, дальше источник — приложение.** Справочник не часть проекта и не часть расчётов: хранится в своём ключе (`stroysmeta:kb`), свой файл в Gist, свои копии. Причины: объём (~1 МБ текста не должен раздувать проект, его точки отката и облачный файл проекта), разный жизненный цикл (знания меняются редко, проект — постоянно), приватность. Повторного импорта из Obsidian нет (загрузка файла заменяет справочник целиком с копией перед заменой).
- **D27 · 2026-10-18 · Справочник ничего не подставляет в расчёты.** Нормы расхода, допуски, сроки в заметках — текст для человека. В формулы и цены они попадают только руками человека (правило «нормы не выдумываем»). «Живые» данные из справочника (чек-лист приёмки, предупреждения, паузы между процессами, подтверждение норм) — отдельные срезы.
- **D28 · 2026-10-18 · Репозиторий публичный: личные данные (справочник, копии проекта) в git не попадают.** Файл справочника грузится в браузере; в `.gitignore` — `stroysmeta-kb*.json`, `*.kb.json`. Связь тема↔технология хранится в справочнике (`topic.techIds`), а не в технологии, чтобы не плодить версии технологий (D23).
- **D29 · 2026-10-18 · Основной адрес сайта — новое приложение.** `index.html` теперь новое приложение, старое — `old.html` (данные те же: тот же origin и ключи localStorage; в старом есть ссылка «Новое приложение →», в новом — ссылка на старое во вкладке «Данные»). `new.html` оставлен как переадресация на `index.html` (старые закладки). Переключение сделано потому, что перенос данных (технологии, объекты, Excel, облако, откаты, справочник) готов; старый UI отключается окончательно позже (Фаза 11). Это уточняет D11.
- **D30 · 2026-10-18 · Допуски из справочника — протокол замеров без автооценки.** Пункты приёмки из заметок берутся как есть (текст пункта + группа); у пунктов из групп «допуски» добавляется поле «замер» (текст). Числа допуска из текста не разбираются и не сравниваются автоматически: на реальных данных допуски — диапазоны, «на 1 м», несколько условий в строке (автоматический вердикт ошибался бы). Пункты приёмки хранятся у пункта плана (`accept`, `measure`), а не в технологии/версии (D23) и не в справочнике: справочник остаётся справкой (D27). Условия и частые ошибки показываются справкой, в движок правил не подставляются.
- **D31 · 2026-10-18 · Подтверждение норм — отметка человека, не данные расчёта.** Строки норм берутся из раздела «Инструменты, материалы и нормы расхода» связанных тем справочника и только показываются. «Подтверждено» = человек прочитал норму, сам ввёл расход/цену в технологии и поставил отметку; хранится в проекте (`S.normOk`), а не в технологии/версии (D23) и не в справочнике (D27, D28). Расход и цена остаются пустыми (UNKNOWN), пока их не введёт человек; числа из текста норм не разбираются.
