# ТЗ «Помощник строителя» — источник истины

> Это исходное ТЗ владельца, сохранено дословно по смыслу. Менять его может только владелец.
> Как мы его реализуем — в `ARCHITECTURE.md`, `DECISIONS.md`, `ROADMAP.md`.

Задача: не добавить несколько функций, а развить приложение до полноценного универсального инструмента строителя/прораба.

**Важно**
- Не переписывать с нуля без необходимости; сохранять работающее; перед крупными изменениями определять, что можно переиспользовать.
- Не создавать сервер/backend/БД/build-систему без явной необходимости. Запуск и размещение на GitHub Pages максимально простые. Основная логика client-side.
- Данные хранятся локально и поддерживают существующий cloud sync.
- Никаких заглушек вместо реально работающих функций.
- Не ограничивать иерархии одним-двумя уровнями.
- Ванная из примера — тестовый объект для проверки универсальности, не хардкодить.

## 1. Цель продукта
Универсальный рабочий инструмент для строительства и ремонта частного дома/квартиры. Не калькулятор, не смета, не каталог, не список технологий. Система:

ОБЪЕКТ → текущее состояние → что хочет получить пользователь → какие процессы нужны → какие технологии подходят → какие операции → материалы/инструменты/работы → расчёт → закупка → выполнение → фактический результат → обновление состояния объекта.

Главный принцип: **система понимает состояние объекта и предлагает следующие допустимые действия.** Не «выбрал стяжку → показать все операции стяжки», а «текущее состояние пола + желаемый результат → необходимые процессы → технологии → последовательность работ».

## 2. Главный принцип архитектуры
Разделять и не смешивать: OBJECT, CONSTRUCTION MODEL / CURRENT STATE, PROCESS, TECHNOLOGY, OPERATION, MATERIAL REQUIREMENT, MATERIAL PRODUCT, TOOL, RULE, FORMULA, ESTIMATE, PURCHASE, WORK EXECUTION, OBSERVATION, GEOMETRY.

**Object** — конкретный объект: квартира, дом, ванная, помещение, ремонт.

**Geometry** — параметрическая геометрическая модель: помещения, стены, перегородки, полы, потолки, двери, окна, проёмы, ниши, короба, поверхности, зоны. Меняется длина стены 4.0→4.5 м — все зависимые площади/периметры/объёмы/расчёты пересчитываются. Площадь не хранится как ручное значение, если выводится из геометрии. Нужен простой 2D-планировщик сверху (НЕ AutoCAD): стены, размеры, углы, помещения, двери, окна, перегородки, короба, зоны, привязки, автоматические размеры, редактирование мышью/тачем, ручная корректировка. Геометрия семантическая, не набор пикселей.

**Current State** — у объекта есть текущее строительное состояние. Пол: основание, стяжка, гидроизоляция, утепление, тёплый пол, покрытие. Стена: материал основания, штукатурка, шпаклёвка, грунтовка, плитка, краска. Значения: YES / NO / UNKNOWN / NOT_APPLICABLE. **UNKNOWN != NO** (если пользователь не знает, есть ли гидроизоляция — система не считает её отсутствующей).

**Observation** — существующие элементы, созданные не нашим проектом («существующая стяжка примерно 55 мм»): стяжка, плитка, ГКЛ, электрика, перегородка. Система умеет начинать с уже существующего объекта (вторичное жильё).

## 3. Process / Technology / Operation
- **Process** — что изменить/получить: сделать стяжку, облицевать стену плиткой, покрасить стену, потолок из ГКЛ, демонтировать плитку, гидроизоляция, тёплый пол.
- **Technology** — как выполнить Process (стяжка: мокрая, полусухая, сухая; наружная стена: кирпич, газоблок). Имеет: prerequisites, inputs, outputs, state changes, operations, material requirements, tools, conditions, rules, warnings, acceptance criteria.
- **Operation** — отдельная работа внутри технологии (полусухая стяжка: подготовка основания, очистка, грунтование, демпферная лента, маяки, армирование, смесь, укладка, выравнивание, затирка, уход). Может иметь: work unit, work price, quantity formula, materials, tools, conditions, errors, acceptance criteria, notes. Отдельно рассчитываемая работа.

## 4. Technology graph
Дерево — только UI-представление каталога. Фактические связи — **граф**. Процессы могут: требовать другие процессы, создавать состояния, запрещать технологии, рекомендовать другие, иметь альтернативы, вести к разным downstream-маршрутам. RAW BRICK WALL → PLASTER → PUTTY → SANDING → PRIMER → PAINT; но если уже EXISTING ACCEPTED PUTTY → SANDING → PRIMER → PAINT. Лишние процессы не выполнять.

## 5. State changes / effects
Технология/операция меняет состояние. Эффекты: ADD, REMOVE, SET, CHANGE, CREATE, DESTROY. Примеры: создать/удалить стену, перегородку, дверной проём, закрыть проём, создать/объединить помещения, установить стяжку, удалить плитку, установить тёплый пол, создать гидроизоляцию, установить плитку, создать окрашенную поверхность. **Демонтаж — полноценный Process**, не исключение.

## 6. Rule engine
Универсальный структурированный механизм правил, **не хардкодить строительные правила в UI**. Условия: IF, AND, OR, NOT, сравнения, IN, EXISTS, UNKNOWN. Действия: REQUIRE, RECOMMEND, FORBID, ADD_PROCESS, ADD_OPERATION, ADD_MATERIAL, ADD_TOOL, WARN, SET_VALUE, MODIFY_QUANTITY, MODIFY_COEFFICIENT.
Примеры: `IF room.type == bathroom AND surface.target == tile THEN REQUIRE waterproofing`; `IF screed.thickness > 50mm THEN RECOMMEND reinforcement`.
Каждое автодобавленное действие имеет объяснение: «Гидроизоляция добавлена, потому что помещение — влажная зона и выбран данный маршрут». Пользователь понимает, ПОЧЕМУ.

## 7. Smart next actions
Для каждого объекта: Готово / В работе / Можно выполнить / Требует уточнения / Заблокировано / Рекомендуется. Пример «Покраска стены»: ✓ основание определено, ✓ шпаклёвка завершена, ✓ шлифовка завершена, ? неизвестно состояние грунтовки → «Уточнить состояние грунтовки». Или «Плитка заблокирована: основание стены ещё не подготовлено».

## 8. Questions / missing data
НЕ заставлять заполнять огромную анкету. Спрашивать только то, что нужно для следующего расчёта/решения. «Хочу плитку на стене»: система знает геометрию, высоту, материал стены, не знает состояние основания → спрашивает только это. Формат плитки — позже. Размер зуба шпателя — только если влияет на выбранную модель расчёта.

## 9. Materials
Разделить MATERIAL REQUIREMENT («плиточный клей: X кг/м²») и MATERIAL PRODUCT («Ceresit X: мешок 25 кг»). Бренд меняется без изменения технологии. Material: name, category, unit, package, package quantity, consumption, regional average price, price date, supplier, notes. В будущем: история цен, фактическая цена покупки, поставщик.

## 10. Formulas
Не только строки: структурированное представление/AST. Пользовательский вид: `area * thickness * consumption`. Поддержать: параметры объекта, геометрию, свойства поверхностей, технологические параметры, коэффициенты, условные значения, единицы измерения. Объяснение пользователю: «Площадь 42 м² × толщина 50 мм × расход 1.9 кг/м² на 10 мм = … кг».

## 11. Units / packaging
Отделить расчётную потребность от покупки упаковок: need = 395 kg, package = 25 kg, purchase = ceil(395/25) = 16 bags. Поддержать преобразования единиц.

## 12. Waste / reserve
Разделять TECHNOLOGICAL WASTE и RESERVE (плитка: 5% подрезка + 5% запас). Не смешивать в один коэффициент без объяснения.

## 13. Estimate
Estimate — снимок расчёта, не источник истины. Отдельно: MATERIALS, CONSUMABLES, WORK, TOOLS/EQUIPMENT. Поддержать: reserve, overhead, discount, VAT, packaging rounding. Цена материала изменилась позже — старая утверждённая смета не меняется.

## 14. Purchases
Учитывать: required, purchased, used, remaining, to_buy. Ceresit: required 8, purchased 2, to_buy 6. При пересчёте технологии потребность обновляется, история реально купленного не уничтожается.

## 15. Work execution
Смета и выполнение — разные сущности. Статусы: PLANNED, READY, IN_PROGRESS, COMPLETED, ACCEPTED. Поддержать planned/actual quantity, planned/actual cost, planned/actual material consumption. После завершения работы состояние объекта обновляется.

## 16. Checklist / acceptance
У технологии может быть checklist (стяжка: очищена, маяки, толщина, перепады, затёрта, дефектов нет). ACCEPTED — только после прохождения обязательных критериев.

## 17. Technology versioning
Проект ссылается на конкретную версию технологии. Technology v1 → v2: старый проект не пересчитывается. Нужны immutable/snapshot-семантика применённой технологии.

## 18. Alternative routes
Несколько технологий одной задачи: сравнивать полный downstream route (стоимость, материалы, работа, время, prerequisites, доп. процессы, последствия), не только локальную цену. EXISTING SCREED: A — оставить, B — ремонтировать, C — демонтировать и сделать новую → Route A/B/C и их последствия.

## 19. Object entry points
Не обязан начинать с фундамента. Можно создать: новый дом, объект, квартиру, существующую ванную, объект вторичного жилья. «У меня уже есть ванная, хочу ремонт» → описать существующее состояние и продолжить от него.

## 20. Geometry / 2D planner
Приоритет: 1 стены, 2 помещения, 3 двери, 4 окна, 5 перегородки, 6 короба, 7 размеры, 8 зоны/поверхности. Автоматически: floor area, ceiling area, wall area, perimeter, opening area, room dimensions, surface dimensions. Произвольное число стен (не 4). Изменение геометрии.

## 21. Real test object (обязательный seed/demo/test, НЕ хардкодить как сценарий)
Ванная: высота 2.7 м; 6 стен: 3.5 м кирпич; 0.5 м ГКЛ на каркасе; 0.5 м ГКЛ на каркасе; 3.5 м кирпич; 4.0 м fortan; 4.0 м fortan.
Проёмы: дверь 2.1×0.9; вторая дверь 2.2×0.8; окно 0.5×0.3.

## 22. Сохранить существующий функционал
Дерево технологий, ветвление/шаги, карточки этапов, цены работ, формулы объёмов, нормы расхода, инструменты, условия/ошибки/приёмка, каталоги материалов/инструментов/композитов, параметры объекта, помещения, авто-расчёт пол/потолок/стены/периметр, выбранные этапы, смета, закупка, инструменты, запас, накладные, скидка, НДС, экспорт Excel, импорт Obsidian markdown, точки отката, облако через GitHub Gist. Не удалять; переносить в новую модель.

## 23. Data safety / migrations
Данные пользователя не уничтожать молча. Версионированная схема и миграции: определять старую версию, мигрировать, сохранять неизвестные поля, делать бэкап перед деструктивной миграцией. Не сбрасывать localStorage молча, не подменять облачные данные молча.

## 24. UX
Русский язык. Mobile-first, но удобно на десктопе. Ощущение профессионального рабочего инструмента, не бухгалтерской таблицы. Навигация: ОБЪЕКТ, ПЛАН, СОСТОЯНИЕ, РАБОТЫ, СМЕТА, ЗАКУПКА, МАТЕРИАЛЫ, ТЕХНОЛОГИИ. Главный экран объекта отвечает: 1 что сейчас с объектом, 2 что нужно получить, 3 что уже сделано, 4 что можно делать сейчас, 5 что заблокировано и почему, 6 что купить, 7 сколько стоит, 8 что дальше.

## 25. Стратегия разработки — вертикальные срезы
1 анализ и план · 2 доменная модель (Object, Geometry, Room, Wall, Opening, Surface, Observation, State) · 3 Process/Technology/Operation · 4 State Changes/Effects · 5 Rule engine и next-action · 6 Material requirements + formulas + units + packaging · 7 Estimate и Purchases · 8 Work execution и фактический расход · 9 Technology versioning · 10 2D-планировщик · 11 Миграция существующего функционала/данных · 12 Сквозной сценарий реальной ванной.

## 26. Правила разработки
Не хардкодить бизнес-логику в UI. Не дублировать расчёты. Один источник истины для: геометрии, состояния, определений технологий, требований к материалам, расчётов. Расчётные значения — производные, не хранить одно значение в нескольких независимых местах (кроме явных snapshot/history). Подписи UI не источник доменной логики. Использовать ID/ссылки. Расширяемые структуры вместо частных случаев. Никаких искусственных лимитов (2 уровня, 4 стены, 5 операций, 10 материалов).

## 27. Definition of done
Без хардкодных частных случаев работает: создать новую ванную → описать геометрию и состояние → система выводит геометрические величины → «хочу плиточный пол с водяным тёплым полом» → определяет процессы → находит недостающее → спрашивает только необходимое → пользователь выбирает технологии → создаются экземпляры технологий → генерируются операции → считаются работы/материалы → учитываются уже купленные → потребности закупки → смета → выполнение работ меняет состояние → открываются следующие процессы → если процесс невозможен, объясняет почему → альтернативы можно сравнить маршрутами → изменение геометрии обновляет расчёты → смена продукта не меняет технологию → обновление библиотеки технологий не меняет старый проект → перезагрузка не теряет данные → существующие данные остаются пригодными.

## 28. Первое действие
Не кодить вслепую: сначала изучить проект и дать (1) архитектуру, (2) модель данных, (3) что переиспользовать, (4) конфликты, (5) стратегию миграции, (6) фазы, (7) затрагиваемые файлы, (8) риски и неявные решения. Потом реализация. Не просить заново проектировать архитектуру без настоящего противоречия. Направление продукта намеренное — задача: реализовать.
